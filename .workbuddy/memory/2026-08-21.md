## 封禁实测 + CDN 缓存坑（18:04）
- 用户把设备码 `69cccb82b90f329d` commit 进 banlist.txt，但 App 重启后仍能打开。
- 日志：`isBanned: listSize=1, hit=false` —— 但远端 raw 实际已有设备码。
- 根因：`raw.githubusercontent.com` 走 Fastly CDN，commit 后几分钟内仍返回旧内容；`Cache-Control: no-cache` 请求头不能强制 bust CDN。
- 修复：`BanManager.fetchBannedList()` 给 banUrl 拼 `?t=毫秒时间戳` cache-buster，绕过 CDN。
- 修复后真机验证：`hit=true` + 钉钉「已阻止」告警推送成功，封禁页（深色底 / 设备码 / sauyh@qq.com 申诉邮箱）正确显示（已截图）。

## 复用经验
- 情侣飞行棋的 `BanManager`/`ReportManager` 是可直接套用的现成模板，改包名 + 改 URL/凭据即可。
- 300001 = webhook 不是标准自定义机器人（常见误用 gitlab/其它类型机器人地址）。
- 403 = PAT 只有读无写（GET 200 不代表 POST 能建 issue）。
- **CDN 缓存坑**：GitHub raw commit 后别指望 App 立刻看到，banUrl 必加 `?t=毫秒时间戳` cache-buster。
- **raw CDN 终极方案**（18:14）：`?t=` 只能绕 CDN，源站自身也有延迟。改用 GitHub Contents API（`api.github.com/repos/.../contents/banlist.txt`）→ 实时无延迟，commit 即生效。已验证 `hit=true`。
